# AR-P003 v0.3 — Crossed Reviewer × Case Planning

> **Status:** Development planning only — not frozen.  
> **Snapshot:** 2026-09-20  
> These simulations use the selected binary primary endpoint `correct_completion_by_180s`. The primary timing methodology is now `wall_deadline_with_hidden_sensitivity`, but the simulations do not set the confirmatory reviewer count, case count, minimally meaningful effect/precision target, allocation, stopping rule, or implementation-specific timing/exclusion rules.

AR-P003 is a crossed design: each reviewer evaluates multiple cases, and each case is evaluated by multiple reviewers. Therefore 2,592 reviewer-case observations are **not** 2,592 independent observations.

The earlier research review proposed **72 fresh episodes**, an initial planning target of **108 reviewers**, and **24 episodes per reviewer**, yielding 2,592 reviewer-case observations. That proposal remains a planning center only. Final counts still require design-specific sensitivity analysis plus a frozen endpoint/effect target.

## New design-specific planner

The repository now includes:

- `benchmark/arp003_v0_3/plan_crossed_design.py`
- `benchmark/arp003_v0_3/crossed-planning-scenarios.example.json`

The planner uses the same balanced incomplete-block assignment generator as the development study pipeline, then simulates a binary endpoint with explicit reviewer and case random intercepts.

For each simulated dataset it estimates three raw-baseline linear-probability contrasts with two-way cluster-robust covariance:

- structured vs raw;
- Receipt vs raw;
- Receipt vs structured.

```text
V_two_way = V_reviewer + V_case - V_reviewer×case
```

This is the standard additive two-way cluster covariance structure described by Cameron, Gelbach, and Miller and implemented by tools such as `statsmodels.stats.sandwich_covariance.cov_cluster_2groups`.

References:

- Cameron, Gelbach & Miller, *Robust Inference with Multi-way Clustering*: https://www.nber.org/papers/t0327
- statsmodels `cov_cluster_2groups`: https://www.statsmodels.org/dev/generated/statsmodels.stats.sandwich_covariance.cov_cluster_2groups.html

The repository implementation is dependency-light and coded directly for the three-condition development contrast set. It is not a replacement for the final statistical-analysis implementation.

## Simulation model

Each synthetic binary response uses:

```text
logit(P(success)) =
    baseline
  + reviewer random intercept
  + case random intercept
  + condition effect
```

Inputs include:

- reviewer count;
- case count;
- cases per reviewer;
- assignment seed;
- simulation seed;
- Monte Carlo iterations;
- conditional raw success probability;
- conditional structured-control success probability;
- conditional Receipt success probability;
- reviewer random-effect SD on the logit scale;
- case random-effect SD on the logit scale;
- two-sided alpha.

The assignment generator is run once per scenario. Every Monte Carlo replicate then draws new reviewer/case effects and new binary outcomes on that fixed randomized design.

## Outputs

For each scenario the planner reports:

- total reviewer-case observations;
- assignment-balance diagnostics;
- assumed conditional probabilities and odds ratio;
- reviewer and case heterogeneity assumptions;
- mean simulated marginal success probabilities;
- mean estimated risk difference;
- empirical SD of the risk-difference estimator;
- median two-way cluster-robust standard error;
- two-sided rejection rate;
- directional rejection rate;
- Monte Carlo SE of the two-sided rejection rate;
- unusable variance iterations, if any.

The rejection rate is a **planning sensitivity metric**, not a promised confirmatory power guarantee.

## Why this is better than the earlier screening grid

The existing `plan_sample_size.py` intentionally treats observations as independent and optionally inflates them with a generic design-effect multiplier.

The crossed planner improves that by explicitly representing:

- reviewer-level dependence;
- case-level dependence;
- the actual balanced incomplete-block assignment;
- two-way clustered uncertainty.

It therefore addresses the previously open engineering portion of the reviewer × case planning gate.

It does **not** close the downstream planning/freeze gates because the following assumptions are still not frozen:

- implementation-specific timing/exclusion rules and browser/device behavior under the selected wall clock;
- minimally meaningful effect or precision target;
- baseline human performance;
- plausible reviewer heterogeneity;
- plausible case heterogeneity;
- reviewer/case allocation;
- attrition/exclusion behavior;
- final analysis model.

The target population is now selected as relevant professional reviewers. That selection scopes future planning but does not provide baseline performance/variance estimates, select professional-domain quotas, or determine final allocation.

## Illustrative scenario grid

The bundled scenario file is deliberately a sensitivity grid, not a recommendation.

It centers one set of scenarios on the earlier **108 reviewer / 72 case / 24 cases-per-reviewer** proposal and varies:

- reviewer count: 72, 108, 144;
- reviewer/case heterogeneity;
- a smaller condition-effect assumption.

The example uses illustrative raw / structured / Receipt conditional probabilities (commonly 0.70 / 0.75 / 0.80) only to exercise sensitivity. Those values are **not** evidence-derived estimates and are not frozen.

Run:

```bash
python benchmark/arp003_v0_3/plan_crossed_design.py --self-test
```

Run the illustrative grid:

```bash
python benchmark/arp003_v0_3/plan_crossed_design.py \
  benchmark/arp003_v0_3/crossed-planning-scenarios.example.json
```

## Interpretation rule

A favorable simulated rejection rate is not evidence that Activity Receipts work.

It means only:

> Under the stated synthetic performance and heterogeneity assumptions, this reviewer × case allocation would often produce a detectable condition contrast under the planner's simplified analysis approximation.

A low rate can be useful too: it indicates that the assumed design/effect combination may be too weak for a confirmatory claim.

## Relationship to final analysis

The final preregistered analysis should still account for both reviewer and case dependence.

Candidate approaches remain:

- a prespecified crossed mixed-effects model when its assumptions and implementation are appropriate;
- a prespecified two-way cluster-robust model for suitable endpoints;
- a cluster-respecting resampling strategy.

The final model must be chosen before confirmatory outcomes are inspected.

## Gate status after this work

The **crossed-design planning tooling** can now be described as prepared.

The **crossed-design power/sample-size decision** remains incomplete because the effect/precision target and variance assumptions are unresolved.

Do not change the freeze-readiness state to `complete` on the basis of this tool alone.


## Three-condition methodology update — 2026-09-20

The comparison-condition architecture is now explicitly selected as `three_condition_structured_control`.

Planner version `AR-P003-v0.3-crossed-planning-v0.3` therefore reports all three development contrasts, including the two needed to separate generic structuring from Receipt-specific incremental presentation:

```text
structured - raw
Receipt - structured
```

`Receipt - raw` is retained as a total presentation contrast.

This planner update does not choose the primary endpoint, minimally meaningful effect, final sample size, or confirmatory analysis model. The reviewer population was subsequently selected as relevant professional reviewers, but the population selection alone does not resolve those planning inputs.


## Integrated challenge-design update — 2026-09-21

The challenge architecture is now selected as `integrated_challenge_strata`: ordinary and stale/incomplete/conflicting challenge cases remain inside one crossed study.

The planner records that selection, but the example simulations still do **not** model or freeze final challenge-stratum counts/allocation. This is deliberate: reviewer/case counts, stratum allocation, effect target, and final power/precision remain unresolved.

Accordingly, the challenge-strata freeze gate remains open even though the architecture decision is selected.
