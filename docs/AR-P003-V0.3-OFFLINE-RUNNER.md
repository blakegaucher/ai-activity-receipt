# AR-P003 v0.3 — Development Offline Runner

> **Status:** Development-only runner; not a frozen confirmatory instrument.  
> **Snapshot:** 2026-09-18  
> This runner does not establish that Activity Receipts improve human auditing.

The v0.2.3 human runner had several timing and interface problems: no safe breaks, no visibility/pause tracking, and manual raw-JSON answer entry. The v0.3 development runner is designed to remove those avoidable confounds before any confirmatory freeze.

## Reviewer-facing / analysis-side separation

The browser bundle is intentionally reviewer-facing only.

It may contain:

- pseudonymous reviewer ID;
- protocol version;
- case IDs;
- reviewer evidence artifacts;
- optional Activity Receipt;
- selectable action/source/incident vocabularies.

It must **not** contain:

- gold labels;
- hidden case stratum;
- expected answer;
- Receipt-state label;
- analysis-only files;
- answer keys.

The validator rejects prohibited analysis-side keys and duplicate case IDs.

Gold reconstruction and hidden stratum live in a separate analysis bundle that is never loaded by the reviewer browser.

## Offline execution

The runner is a single static HTML file with no external script, stylesheet, API, telemetry endpoint, or hosted dependency.

The development validator checks for:

- a Content Security Policy with `connect-src 'none'`;
- no external `script src`;
- no `fetch`, XHR, WebSocket, or beacon calls;
- explicit pause controls;
- visibility tracking;
- local response download;
- text-only rendering of evidence content rather than HTML injection.

The runner uses browser file input and local Blob download only.

## Timing model

For each case the runner records:

- case presentation timestamp;
- final submission timestamp;
- wall elapsed seconds;
- active elapsed seconds;
- manual pause events;
- browser hidden/visible events;
- a reviewer technical-issue flag.

A case automatically pauses when the page becomes hidden.

Manual and visibility pauses can overlap without double-counting paused time.

The runner does **not** start the next case immediately after submission. It enters an intermission screen, and the next timer begins only when the reviewer explicitly starts the next case.

This creates a safe break point between every case.

## Structured response UI

The development runner uses structured controls for:

- material actions;
- authorization violation;
- material sources;
- incidents;
- verification state;
- missing-evidence state;
- confidence;
- technical issue flag.

Reviewers do not edit raw JSON.

That removes JSON syntax/typing overhead from the reconstruction task.

## Condition neutrality

The runner does not tell reviewers that one condition is expected to be better.

When a Receipt is included, it is presented as another artifact to inspect.

Reviewer instructions continue to state that every artifact is evidence, not guaranteed ground truth.

This is necessary for stale, incomplete, and conflicting Receipt challenge cases.

## Response export

The reviewer downloads a JSON response export containing no gold labels.

The analysis-side merge utility later joins that export to the hidden analysis bundle:

```bash
python benchmark/arp003_v0_3/merge_runner_responses.py \
  reviewer-responses.json \
  hidden-analysis.json \
  --timing active \
  --output scorer-input.jsonl
```

The `--timing` choice is mandatory. This prevents the analysis path from silently deciding after the fact whether wall or active time is the scored timing field.

For the current protocol direction, active time is the intended primary timing interpretation, but the final choice must be frozen in the analysis plan before confirmatory execution.

## Development validation

Run:

```bash
python benchmark/arp003_v0_3/validate_runner_data.py --self-test
python benchmark/arp003_v0_3/merge_runner_responses.py --self-test
```

These tests cover:

- reviewer/analysis data separation;
- duplicate case IDs;
- duplicate evidence labels;
- basic timing consistency;
- static offline/no-network runner markers;
- protocol-version mismatch;
- missing hidden analysis records;
- active-vs-wall timing mapping;
- compatibility with the existing scoring-record schema.

## What still must be tested manually

Static and Python self-tests cannot prove browser behavior.

Before freeze, the runner still needs at least:

- desktop browser smoke test;
- mobile/tablet smoke test if those devices will be allowed;
- pause/resume test;
- tab-background/visibility test;
- download/reload-loss test;
- long evidence scrolling test;
- keyboard/accessibility review;
- structured-option readability review;
- test that no submitted case can be revisited;
- test that an intermission break does not contaminate the next case timer.

Any browser compatibility requirement must be frozen with the final study protocol.

## Evidence boundary

A well-behaved runner solves an instrumentation problem. It does not establish:

- that the cases are realistic;
- that the gold labels are correct;
- that the study is adequately powered;
- that the target reviewer population is appropriate;
- that ethics review is complete;
- that Receipt presentation improves outcomes.

Those remain separate preregistration and external/human evidence gates.
