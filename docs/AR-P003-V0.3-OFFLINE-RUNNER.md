# AR-P003 v0.3 — Development Offline Runner

> **Status:** Development-only runner; not a frozen confirmatory instrument.  
> **Snapshot:** 2026-09-18  
> This runner does not establish that Activity Receipts improve human auditing.

The v0.2.3 human runner had several timing and interface problems: no safe breaks, no visibility/pause tracking, and manual raw-JSON answer entry. The v0.3 development runner is designed to remove those avoidable confounds before any confirmatory freeze.

## Reviewer-facing / analysis-side separation

The browser bundle is intentionally reviewer-facing only.

It may contain:

- pseudonymous reviewer ID;
- protocol version;
- case IDs;
- reviewer evidence artifacts;
- optional Activity Receipt;
- selectable action/source/incident vocabularies.

It must **not** contain:

- gold labels;
- hidden case stratum;
- expected answer;
- Receipt-state label;
- analysis-only files;
- answer keys.

The validator rejects prohibited analysis-side keys and duplicate case IDs.

Gold reconstruction and hidden stratum live in a separate analysis bundle that is never loaded by the reviewer browser.

## Offline execution

The runner is a single static HTML file with no external script, stylesheet, API, telemetry endpoint, or hosted dependency.

The development validator checks for:

- a Content Security Policy with `connect-src 'none'`;
- no external `script src`;
- no `fetch`, XHR, WebSocket, or beacon calls;
- explicit pause controls;
- visibility tracking;
- local response download;
- text-only rendering of evidence content rather than HTML injection.

The runner uses browser file input and local Blob download only.

## Pre-case comprehension gate

After a valid reviewer bundle is loaded, the first timed case does **not** begin immediately.

The reviewer must correctly answer three neutral instruction checks:

1. a Receipt that conflicts with underlying evidence is not automatically trusted;
2. private chain-of-thought is not requested;
3. active timing can pause through explicit Pause/Resume or when the page is hidden.

Incorrect attempts return the reviewer to the same instruction check without exposing gold case labels.

Only after all three answers are correct does the runner record `comprehension.passed_at`, set the session start time, and begin case 1.

The response export records:

- `gate_version`;
- `attempts`;
- `passed_at`.

The answers themselves are not exported.

The analysis-side merge rejects a response with no valid comprehension-gate record.

This is an instrumentation/comprehension safeguard, not a scored study endpoint.

## Untimed structured practice case

After the comprehension gate, the development runner presents one fixed synthetic practice reconstruction before any assigned study case begins.

The practice case uses the same structured response concepts as the study interface:

- material actions;
- authorization-violation state;
- material sources;
- incidents;
- verification state;
- missing-evidence state.

It deliberately omits a confidence score and is not included in the study case list.

The practice example is **untimed**. The session/case timer begins only after the practice answer is correct.

Incorrect attempts return the reviewer to the same practice example with a neutral error message. The exported response records only:

- `practice_version`;
- attempt count;
- pass timestamp.

The practice answer itself is not exported and cannot enter the scorer.

The current training example is development-only and must be reviewed/frozen with the final reviewer instructions so it does not create unintended answer-pattern coaching.

## Timing model

For each case the runner records:

- case presentation timestamp;
- final submission timestamp;
- wall elapsed seconds;
- active elapsed seconds;
- manual pause events;
- browser hidden/visible events;
- a reviewer technical-issue flag.

A case automatically pauses when the page becomes hidden.

Manual and visibility pauses can overlap without double-counting paused time.

The runner does **not** start the next case immediately after submission. It enters an intermission screen, and the next timer begins only when the reviewer explicitly starts the next case.

This creates a safe break point between every case.

## Structured response UI

The development runner uses structured controls for:

- material actions;
- authorization violation;
- material sources;
- incidents;
- verification state;
- missing-evidence state;
- confidence;
- technical issue flag.

Reviewers do not edit raw JSON.

That removes JSON syntax/typing overhead from the reconstruction task.

## Condition neutrality

The runner does not tell reviewers that one condition is expected to be better.

When a Receipt is included, it is presented as another artifact to inspect.

Reviewer instructions continue to state that every artifact is evidence, not guaranteed ground truth.

This is necessary for stale, incomplete, and conflicting Receipt challenge cases.

## Building reviewer bundles from assignments

The development bundle builder connects the existing assignment generator and case-package manifests to the offline runner without manually copying evidence into reviewer files.

Inputs:

- seeded assignment JSON from `generate_assignment.py`;
- lintable case-package manifests;
- a runner build config that points to each case manifest, hidden gold file, and reviewer-facing answer-option vocabulary.

Run:

```bash
python benchmark/arp003_v0_3/build_runner_bundles.py \
  assignment.json \
  runner-build-config.json \
  --output-dir runner-build
```

The builder:

- validates every referenced case package;
- requires assignment stratum to match the hidden case manifest;
- preserves shared evidence symmetry;
- includes the Receipt only for Receipt-condition assignments;
- keeps gold labels and hidden strata out of every reviewer bundle;
- writes hidden gold/stratum data to `analysis/runner-analysis.json`;
- writes SHA-256 hashes for assignment/config inputs and generated reviewer/analysis artifacts to `build-manifest.json`;
- refuses to overwrite an existing output directory.

The current runner supports UTF-8 text/Markdown/JSON evidence artifacts only. Image, audio, PDF, and other rich-media study evidence need a separately specified presentation path before use.

## Exact assignment binding

Each generated reviewer bundle now carries:

- the assignment version;
- the SHA-256 digest of the exact assignment JSON used to build it.

The offline runner copies those fields into the response export.

During analysis, `merge_runner_responses.py` requires the exact assignment file and rejects:

- a response whose assignment digest/version does not match;
- a reviewer not present in the assignment;
- missing or extra assigned cases;
- case-order changes;
- a reviewer-edited control/Receipt condition label;
- a hidden stratum that disagrees with the frozen assignment;
- an incomplete session with no final completion timestamp.

This closes an important development integrity gap: analysis no longer trusts the condition label stored in the reviewer export as the source of truth. The frozen assignment is authoritative.

## Response export

The reviewer downloads a JSON response export containing no gold labels.

The analysis-side merge utility later joins that export to the hidden analysis bundle:

```bash
python benchmark/arp003_v0_3/merge_runner_responses.py \
  reviewer-responses.json \
  hidden-analysis.json \
  frozen-assignment.json \
  --timing active \
  --output scorer-input.jsonl
```

The exact assignment file and the `--timing` choice are both mandatory. The assignment file is used to verify case/order/condition integrity; the timing switch prevents the analysis path from silently deciding after the fact whether wall or active time is the scored timing field.

For the current protocol direction, active time is the intended primary timing interpretation, but the final choice must be frozen in the analysis plan before confirmatory execution.

## Development validation

Run:

```bash
python benchmark/arp003_v0_3/validate_runner_data.py --self-test
python benchmark/arp003_v0_3/merge_runner_responses.py --self-test
```

These tests cover:

- reviewer/analysis data separation;
- duplicate case IDs;
- duplicate evidence labels;
- basic timing consistency;
- static offline/no-network runner markers;
- protocol-version mismatch;
- missing hidden analysis records;
- active-vs-wall timing mapping;
- compatibility with the existing scoring-record schema.

## What still must be tested manually

Static and Python self-tests cannot prove browser behavior.

Before freeze, the runner still needs at least:

- desktop browser smoke test;
- mobile/tablet smoke test if those devices will be allowed;
- pause/resume test;
- tab-background/visibility test;
- download/reload-loss test;
- long evidence scrolling test;
- keyboard/accessibility review;
- structured-option readability review;
- test that no submitted case can be revisited;
- test that an intermission break does not contaminate the next case timer.

Any browser compatibility requirement must be frozen with the final study protocol.

## Evidence boundary

A well-behaved runner solves an instrumentation problem. It does not establish:

- that the cases are realistic;
- that the gold labels are correct;
- that the study is adequately powered;
- that the target reviewer population is appropriate;
- that ethics review is complete;
- that Receipt presentation improves outcomes.

Those remain separate preregistration and external/human evidence gates.
