## 1. Comparison conditions

### Two-condition current implementation

Current development tooling compares:

1. underlying heterogeneous evidence;
2. the same evidence plus Activity Receipt.

**Engineering advantage:** already implemented and tested.

**Methodological limitation:** an observed benefit could reflect generic evidence organization/presentation rather than something specific to the Receipt.

### Three-condition structured control

The earlier research review proposed:

1. raw/underlying evidence;
2. a neutral structured event table plus the same underlying evidence;
3. Receipt plus the same underlying evidence.

The purpose is to separate:

- benefit from **structuring evidence at all**;
- additional benefit attributable to the **Receipt's semantic/presentation profile**.

The project owner selected this option on 2026-09-20. The selection is recorded in the methodology ledger and implemented through a new versioned protocol/assignment/runner/bundle/scorer/planning path. The neutral table must derive from the same underlying record/evidence as the Receipt so it does not receive oracle information.

This document remains decision support rather than the selection authority; the ledger and explicit owner decision are authoritative.

## 2. Primary endpoint

### Component endpoint set

The current scorer already preserves:

- material-action set performance;
- material-source set performance;
- incident-set performance;
- authorization-violation accuracy;
- verification-state accuracy;
- missing-evidence accuracy;
- timing.

A confirmatory use would still need a small frozen primary set, multiplicity handling, and explicit claim gates.

### Evidence-supported correct completion by 180 seconds

The earlier research review proposed one interpretable primary endpoint: **supported, correct audit completion by 180 seconds**.

That candidate requires all required judgments to be correct, supporting evidence to be adequate, no material event/authorization to be fabricated, and timeout to fail the primary endpoint. The same review separately proposed **critical false clearance** as a safety endpoint.

The project owner selected this option on 2026-09-21. The versioned development implementation now represents frozen-per-case required judgments/evidence sets, preserves component outcomes as secondary diagnostics, and keeps critical false clearance separate. The primary timing clock remains explicitly unresolved, so confirmatory primary scoring still fails closed.

**Do not derive this outcome post hoc from component scores after seeing results.**

## 3. Primary timing clock

The development runner already records both wall and active time, so development data collection does not force the final choice.

### Active-time primary

Would exclude intervals frozen as eligible manual/visibility pauses.

It requires:

- exact pause eligibility;
- technical-failure/exclusion rules;
- browser/device smoke verification.

### Wall deadline with hidden-time sensitivity

The research review proposed retaining background/hidden elapsed time in the primary deadline and prespecifying a sensitivity analysis for trials with more than 10 seconds hidden.

This option also requires:

- timeout behavior;
- last-answer-state capture;
- reload/timer-context-break rules;
- hidden-time sensitivity analysis.

Because both clocks are recorded, choosing later **before confirmatory outcomes** need not discard development observability.

## 4. Misleading-Receipt robustness

### Integrated challenge strata

Current development architecture includes stale, incomplete, and conflicting Receipt strata in the broader assignment and can report ordinary/challenge cases separately.

The project owner selected this integrated architecture on 2026-09-21. Final challenge-stratum counts/allocation and final-corpus review remain open freeze requirements.

The project owner selected this integrated architecture on 2026-09-21. Final challenge-stratum counts/allocation and final-corpus review remain open freeze requirements.

### Separate robustness cohort

The research review proposed a separate experiment with fresh families/episodes comparing:

- raw-only;
- faithful Receipt + raw evidence;
- corrupted Receipt + raw evidence.

The review's corruption taxonomy also extends beyond stale/incomplete states to authority/gate error, verification error, evidence mismatch, and integrity/identity mismatch.

A separate cohort materially changes sampling, error prevalence, assignment, and interpretation, so it cannot be introduced as a silent implementation tweak.

## 5. Reviewer population

### Preserved unresolved placeholder

The earlier ledger state used `population_to_be_selected` to keep the following requirements visible:

- intended population of inference;
- eligibility/exclusion criteria;
- expertise strata;
- language proficiency;
- project-familiarity rule;
- exclusion of case constructors/scorers;
- external-AI-assistance rule.

A convenience sample must not later be described as representative of a professional audit population without justification.

### Relevant professional reviewers

The project owner selected `relevant_professional_reviewers` on 2026-09-21. The selected criteria require at least 1 year of relevant practical/professional experience in a listed audit, cybersecurity, compliance, AI-governance, incident-review, software/system-operations, technical-assurance, or closely related evidence-review domain. The protocol records 1–2, 3–5, and 6+ year bands; sufficient English; no mandatory degree/certification/job title; permitted-and-recorded prior general AI Activity Receipt familiarity; conflict/exposure exclusions; and no external web, AI, person, tool, or outside-evidence assistance during study cases.

The selection completes the population decision, not recruitment or allocation. Claims remain limited to the professional population actually recruited.

## 6. Meaningful effect / precision target

The current repository intentionally leaves the target open.

The research review provides one explicit **candidate** set of preregistration decision assumptions:

- **+5 percentage points**: proposed smallest practically important increase in supported completion;
- **3 percentage points**: proposed accuracy noninferiority margin for a separate speed claim;
- **+2 percentage points**: proposed maximum acceptable increase in critical false clearance.

The review explicitly says these are **decision assumptions, not industry norms**, and their acceptability should be confirmed before confirmatory outcomes.

It also proposes crossed-design planning over candidate reviewer counts **108 / 216 / 324 / 432**, using at least **1,000 simulation replicates per decision-relevant scenario**, plus baseline/heterogeneity sensitivity.

These values are now preserved as an unresolved ledger candidate. They are **not selected** and are **not estimates from AR-P003 v0.2.3**.

## 7. Safe decision sequence

A future methodology-selection session should resolve the choices in dependency order:

1. comparison conditions — **selected: three-condition structured control**; challenge design — **selected: integrated challenge strata**;
2. target reviewer population — **selected: relevant professional reviewers**;
3. primary endpoint — **selected: correct completion by 180 seconds**; timing semantics remain unresolved;
4. meaningful effect / safety / precision thresholds;
5. crossed-design planning and sample allocation;
6. corpus construction and leakage/manual methodology review;
7. final runner/scorer/instructions/assignment;
8. ethics/REB/IRB review or documented determination as applicable;
9. protocol freeze and content-bound manifest;
10. only then confirmatory human execution.

The order is important because a change to conditions, endpoint, population, or challenge architecture can invalidate downstream power/sample-size work.

## Evidence boundary

This document reduces ambiguity about what each candidate would require.

It does **not**:

- select a methodology;
- establish that one design is superior;
- freeze a protocol;
- justify an effect size as an industry standard;
- supply ethics approval;
- authorize recruitment or supply recruited reviewers;
- create human evidence;
- change the frozen AR-P003 v0.2.3 baseline.
