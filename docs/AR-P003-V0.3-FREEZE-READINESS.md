# AR-P003 v0.3 — Freeze Readiness and Manual Smoke Evidence

> **Status:** Development governance tooling.  
> **Snapshot:** 2026-09-21.
> These files do not freeze the study and do not constitute human-study evidence.

AR-P003 v0.3 now has two machine-readable controls for the remaining pre-human gates:

1. a **freeze-readiness state** that records whether each required decision/evidence gate is pending, prepared, complete, or formally not applicable;
2. a **manual browser smoke-test record** for environment-specific runner behavior.

The goal is to make it difficult for later work to accidentally call the study "ready", "frozen", or browser-validated when the supporting evidence is still missing.

## Freeze-readiness files

- `benchmark/arp003_v0_3/freeze-readiness.schema.json`
- `benchmark/arp003_v0_3/freeze-readiness.current.json`
- `benchmark/arp003_v0_3/check_freeze_readiness.py`

Run:

```bash
python benchmark/arp003_v0_3/check_freeze_readiness.py
```

The current state is intentionally:

```text
study_status = development_not_ready
```

The current file distinguishes:

- **pending** — the required decision/evidence does not yet exist;
- **prepared** — supporting tooling/draft material exists, but the final decision/evidence is not frozen;
- **complete** — the gate is resolved and has evidence references;
- **not_applicable** — a documented determination establishes that the gate does not apply.

A gate cannot be marked `complete` or `not_applicable` without at least one evidence reference.

### Ready-for-freeze rule

`study_status = ready_for_freeze` is rejected unless every pre-freeze gate except the final manifest is `complete` or `not_applicable`.

### Frozen rule

`study_status = frozen` is rejected unless:

- every required gate is resolved;
- the final freeze-manifest gate is resolved;
- `protocol.json` also declares `frozen = true`;
- the readiness file and protocol version agree.

Conversely, if `protocol.json` becomes frozen while the readiness state does not, the validator fails.

This is a consistency guard; it cannot decide methodology for the project owner.

A separate **methodology decision ledger** now records unresolved source conflicts that must not be settled by implementation drift alone. In particular, the freeze-readiness model includes an explicit comparison-conditions gate. See [AR-P003 v0.3 Methodology Decision Ledger](AR-P003-V0.3-METHODOLOGY-DECISIONS.md).

## Current gate state

The present machine-readable state records:

### Complete

- comparison-condition design: selected and implemented as raw / neutral structured / Receipt over the same underlying evidence;
- reviewer population and eligibility: relevant professional reviewers selected with frozen experience, language, familiarity, exclusion, assistance, and inference-scope rules;
- primary endpoint: `correct_completion_by_180s` selected with binary success/failure semantics, case-specific support contracts, component outcomes kept secondary, and critical false clearance kept separate. The primary timing clock remains unresolved.

### Pending

- minimally meaningful effect or final precision target;
- final reviewer/case counts, allocation, and stopping rule;
- fresh sealed confirmatory corpus;
- real browser/device/accessibility smoke evidence;
- ethics/REB/IRB review or documented determination as applicable.

### Prepared but not frozen

- binary-endpoint crossed planning with illustrative assumptions;
- independent-observation and crossed reviewer × case planning tools;
- mechanical leakage checks;
- challenge-strata design;
- reviewer-instructions draft;
- balanced assignment tooling;
- active/wall timing instrumentation;
- component scorer;
- freeze-manifest utility.

"Prepared" must not be reported as "complete".

## Methodology cross-check

Freeze-readiness validation loads `methodology-decisions.current.json` as a separate source of truth.

The following readiness gates are cross-linked to methodology decisions:

- comparison conditions → `comparison_conditions`;
- reviewer population → `reviewer_population`;
- primary endpoints → `primary_endpoint`;
- effect/precision target → `effect_precision_target`;
- challenge strata → `challenge_design`;
- timing/exclusions → `primary_timing_clock`.

A linked readiness gate cannot be marked `complete` or `not_applicable` while its methodology decision remains unresolved. A synthetic ready/frozen self-test only passes after the methodology ledger is separately resolved.

The checker validates the entire supplied ledger with the canonical methodology
schema and validator before reading its decision statuses. This also applies to
a custom file passed through `--methodology`. Invalid candidate references,
missing rationale/evidence references, duplicate or missing decision IDs, and
malformed ledgers are rejected. The six mandatory decisions cannot be made
optional by changing `pre_freeze_required` to `false`.

An overall `ready_for_freeze` or `frozen` state also requires the ledger status
`methodology_resolved` and selection of every required decision, including any
additional required decisions. Self-tests cover all six linked gates, valid
synthetic ready/frozen states, invalid selections, and custom-ledger CLI inputs.

These checks establish metadata consistency and evidence-reference presence;
they do not verify that a referenced review or approval actually occurred.

This does not choose the methodology; it prevents two governance files from contradicting each other.

## Freeze-manifest v0.2 integrity binding

The freeze-manifest utility now reads the **actual protocol file** instead of hard-coding an abbreviated protocol version.

Files:

- `benchmark/arp003_v0_3/freeze_manifest.py`
- `benchmark/arp003_v0_3/freeze-manifest.schema.json`

Every generated manifest records:

- exact protocol path under the selected root;
- exact protocol version from `protocol.json`;
- protocol SHA-256;
- whether the protocol itself declares `frozen=true`;
- per-artifact size and SHA-256;
- deterministic aggregate artifact-set SHA-256;
- deterministic `freeze_content_id` over protocol identity/hash and the sorted artifact set;
- generation timestamp.

The content ID excludes `generated_at`, so generating the same protocol/artifact set at a different time produces the same content identity.

For an actual final freeze, use:

```bash
python benchmark/arp003_v0_3/freeze_manifest.py \
  --root . \
  --protocol benchmark/arp003_v0_3/protocol.json \
  --require-protocol-frozen \
  --output AR-P003-v0.3-FREEZE-MANIFEST.json \
  <all frozen artifact paths...>
```

`--require-protocol-frozen` fails while `protocol.json` still has `frozen=false`.

The freeze content ID is a deterministic content binding, **not** a digital signature or trusted timestamp.

## Manual browser smoke-test files

- `benchmark/arp003_v0_3/browser-smoke-record.schema.json`
- `benchmark/arp003_v0_3/browser-smoke-record.example.json`
- `benchmark/arp003_v0_3/validate_browser_smoke.py`

The checked-in example is deliberately an **incomplete, not-run template**. It is not evidence that any browser passed.

A real record captures:

- exact runner commit;
- runner SHA-256;
- tester role;
- device class;
- OS;
- browser/version;
- start/end time;
- overall result;
- each required smoke check;
- defects and whether they require a new runner version.

Required checks cover:

- valid bundle load;
- comprehension-gate flow, including retry and transition to practice;
- practice-gate flow, including retry and transition to the first timed case;
- invalid/oversized bundle rejection;
- structured controls;
- manual pause/resume timing;
- visibility pause timing;
- intermission timing boundary;
- progress and final downloads;
- reload/navigation warning;
- long-evidence scrolling;
- keyboard-only navigation;
- visible focus;
- text zoom/responsive behavior;
- prevention of case revisit;
- exported-response schema validation.

Validate a completed record:

```bash
python benchmark/arp003_v0_3/validate_browser_smoke.py \
  path/to/smoke-record.json \
  --require-current-runner-hash
```

A record cannot claim `overall_status = pass` if any required check is failed or not tested. A major/blocking defect also prevents a pass.

## Change-control sequence

When a real gate is resolved:

1. preserve the evidence artifact;
2. update the corresponding gate in `freeze-readiness.current.json`;
3. keep `prepared` versus `complete` distinctions accurate;
4. rerun `check_freeze_readiness.py`;
5. update issue #47 and, for browser testing, issue #38;
6. update continuity;
7. rerun the complete repository validation/reproducibility suite.

Do not mark `ready_for_freeze` merely because the code and schemas are green.

## Hard boundaries

This tooling does **not**:

- select the still-unresolved primary timing clock or effect/precision target;
- recruit or screen reviewers;
- choose an effect size;
- select the methodology assumptions needed to finalize reviewer × case power/sample-size planning;
- conduct browser testing;
- create a sealed corpus;
- obtain ethics/REB/IRB review or a determination;
- collect human data;
- establish Activity Receipt benefit.

It exists to keep those gates visible and mechanically consistent until the required evidence actually exists.
