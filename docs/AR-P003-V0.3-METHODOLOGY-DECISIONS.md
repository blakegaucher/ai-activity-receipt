# AR-P003 v0.3 — Methodology Decision Ledger

> **Status:** Development-only decision control; no methodology choice is frozen.  
> **Snapshot:** 2026-09-19  
> **Purpose:** Preserve material differences between the current repository draft and the earlier project research review so later work cannot silently reconcile them.

AR-P003 v0.3 has reached a point where additional code can accidentally make an **unfrozen design choice look settled**. The repository therefore keeps a machine-readable methodology ledger:

- `benchmark/arp003_v0_3/methodology-decisions.schema.json`
- `benchmark/arp003_v0_3/methodology-decisions.current.json`
- `benchmark/arp003_v0_3/validate_methodology_decisions.py`

The ledger does not choose a design. It records the candidate choices, their evidence source, the current implementation, and whether a deliberate preregistration decision has actually been made.

## Source-of-truth rule

For **current executable behavior**, the current repository is authoritative.

For **historical methodology recommendations**, preserve the supplied project research review:

`AI_Activity_Receipt_Research_and_v03_Protocol.pdf` / `.docx`, dated 2026-09-15.

When those sources differ, do not rewrite one to match the other. Record the conflict and require an explicit future selection before confirmatory freeze.

## Decision 1 — Comparison conditions

### Current repository draft

The executable protocol currently uses two conditions:

1. underlying heterogeneous evidence only;
2. the same underlying evidence plus Activity Receipt.

### Earlier research-review recommendation

The research review recommended adding a **neutral structured-log / canonical event-table control**:

1. raw/underlying evidence;
2. neutral structured event table plus the same raw evidence;
3. Receipt plus the same raw evidence.

The purpose was to distinguish benefit from **organizing evidence** from any additional benefit attributable to the Receipt presentation.

### Current status

**Unresolved.**

The two-condition runner remains the current development implementation. Adding a third condition would materially change assignment, bundle contracts, sample-size planning, scorer/reporting, and possibly corpus requirements. It therefore requires a new explicit protocol decision rather than a silent runner edit.

## Decision 2 — Primary confirmatory endpoint

### Current repository draft

The current protocol reports reconstruction components separately:

- material-action set precision/recall/F1;
- material-source set precision/recall/F1;
- incident set precision/recall/F1;
- exact authorization-violation accuracy;
- exact verification-state accuracy;
- exact missing-evidence accuracy;
- timing under frozen timing rules.

It explicitly avoids a post-hoc weighted composite winner score.

### Earlier research-review recommendation

The research review proposed a single interpretable primary endpoint:

**evidence-supported correct audit completion by 180 seconds**

with all required judgments correct, required evidence supporting the verdict, no fabricated material event/authorization, and timeout unable to pass. It also proposed **critical false clearance** as a safety endpoint.

### Current status

**Unresolved.**

The repository has enough scoring machinery to preserve component outcomes regardless of the eventual primary choice. The final primary endpoint or small prespecified primary endpoint set must be selected before sample-size assumptions and confirmatory freeze are finalized.

## Decision 3 — Primary timing clock

### Current development runner

The runner records both:

- wall elapsed time;
- active elapsed time.

Manual pause and page visibility can pause the active clock. Analysis requires an explicit active-vs-wall timing choice.

### Earlier research-review recommendation

The research review recommended that elapsed background time remain in the primary deadline and that trials with more than 10 seconds hidden be handled through a prespecified sensitivity analysis rather than silently pausing selected trials.

### Current status

**Unresolved.**

Keeping both clocks in development data is intentional. It preserves the evidence required to choose and test a final rule later without selecting the more favorable clock after confirmatory outcomes are visible.

## Decision 4 — Misleading-Receipt robustness design

### Current repository draft

The current protocol integrates prespecified challenge strata:

- stale Receipt;
- incomplete Receipt;
- conflicting Receipt.

Ordinary and challenge results are reported separately.

### Earlier research-review recommendation

The research review proposed a **separate robustness cohort** comparing raw-only, faithful Receipt + raw, and corrupted Receipt + raw presentations using fresh families/episodes.

### Current status

**Unresolved.**

Both designs preserve the question of erroneous reliance, but they have different sampling, assignment, interpretation, and power implications. The architecture must be selected before the sealed corpus and final assignment are frozen.

## Decision 5 — Target reviewer population

The repository requires:

- relevant technical/audit experience bands;
- sufficient language proficiency;
- a rule for project familiarity;
- exclusion of people who constructed or scored sealed cases.

No final target population is selected.

**Status: unresolved.**

Any eventual claim must remain scoped to the population actually recruited.

## Decision 6 — Meaningful effect / precision target

The repository now contains:

- independent-observation screening calculations;
- design-specific reviewer × case Monte Carlo sensitivity tooling.

Those tools deliberately use illustrative assumptions.

v0.2.3 cannot supply a defensible human effect estimate because the auxiliary AI reviewer was at ceiling in both conditions and no human timing data exist.

**Status: unresolved.**

A minimally meaningful effect or precision target must be chosen from a defensible external, development-only, or decision-theoretic basis before final power/sample-size freeze.

## Machine guard

Run:

```bash
python benchmark/arp003_v0_3/validate_methodology_decisions.py
python benchmark/arp003_v0_3/validate_methodology_decisions.py --self-test
```

The validator requires:

- ledger/protocol version agreement;
- all required decision IDs to remain present;
- unique decision and candidate IDs;
- a selected candidate to resolve to a listed candidate;
- selected decisions to have rationale and evidence references;
- unresolved decisions to carry no selected candidate;
- every pre-freeze methodology decision to be selected before the ledger may become `methodology_resolved`;
- no frozen protocol while required methodology decisions remain unresolved.

## Freeze-readiness integration

The freeze-readiness model now includes an explicit **comparison-conditions** gate.

Relevant endpoint, timing, challenge, population, and effect-target gates also point back to the methodology ledger.

This makes the disagreement itself part of the pre-freeze evidence rather than allowing the current implementation to become the de facto methodology merely because code already exists.

## What this does not do

This ledger does not:

- select the structured-log control;
- select the 180-second endpoint;
- select active or wall timing;
- select integrated versus separate challenge cohorts;
- choose reviewer eligibility;
- choose the meaningful effect size;
- freeze sample size;
- obtain ethics review;
- create human evidence.

Those remain deliberate preregistration decisions.

## Change-control rule

When a methodology decision is made:

1. update only that decision from `unresolved` to `selected`;
2. name the selected candidate;
3. record the rationale and evidence references;
4. update the relevant protocol/runner/scorer/assignment artifacts in a **new version if the choice changes methodology**;
5. update freeze-readiness evidence;
6. rerun CI and the reproducibility suite;
7. preserve the rejected alternative and the earlier source recommendation in this ledger;
8. do not reinterpret the frozen v0.2.3 benchmark.

A selected methodology is not evidence that the selected method produces a favorable result.
