## Proposed decision

Select:

`primary_timing_clock = wall_deadline_with_hidden_sensitivity`

Do not select or modify `effect_precision_target` in the same decision.

## Rationale

The selected primary endpoint is explicitly evidence-supported correct audit completion **by 180 seconds**. Wall elapsed time is the more direct operational interpretation of that deadline because it measures whether the reviewer reaches the required supported judgment within the full elapsed task window.

Using pause-adjusted active time as the primary clock would make the confirmatory endpoint depend on pause behavior, tab visibility, and pause-detection implementation. Those signals remain useful for sensitivity analysis and technical-quality review, but should not silently extend the primary deadline.

The development runner already records both wall and active time. Therefore selecting wall time does not discard development observability or prevent prespecified active-time sensitivity analysis.

## Proposed primary timing rule

For the confirmatory primary endpoint, subject to final implementation and freeze:

1. Start the wall clock when the case is made available to the reviewer.
2. Stop the primary clock on valid case submission or at the 180-second deadline.
3. Elapsed background/hidden time remains part of the primary wall deadline.
4. A trial exceeding 180 seconds cannot satisfy the primary endpoint.
5. Preserve `elapsed_active_seconds`, pause events, and visibility events as secondary/sensitivity information.
6. Flag trials with more than 10 seconds hidden for a prespecified sensitivity analysis; do not subtract that time from the primary wall clock.
7. Difficult, slow, incorrect, or unfavorable trials are not exclusions.
8. Genuine timer, reload, corrupted-presentation, or context-break failures require a separately frozen technical-failure rule.
9. The active-time sensitivity result may not replace the primary wall-clock result after outcomes are observed.

## Important implementation boundary

This proposal resolves the **methodology choice only**. It does not by itself complete the timing/exclusions freeze gate.

Before confirmatory execution, a versioned implementation must still:

- update the methodology ledger and protocol version;
- update the public runner/bundle/analysis timing contract;
- define exact 180-second timeout behavior;
- preserve the reviewer answer state needed for a timeout record;
- define hidden-time and reload/context-break flags;
- freeze technical-failure and non-estimable rules;
- update scoring so the primary endpoint is derived from wall elapsed time;
- preserve active-time sensitivity diagnostics;
- verify the allowed browser/device timing behavior;
- rerun CI, reproducibility checks, and manual timing smoke tests;
- update freeze-readiness and continuity records.

Until those steps are complete, the timing/exclusions gate remains open even if this methodology proposal is later selected.
