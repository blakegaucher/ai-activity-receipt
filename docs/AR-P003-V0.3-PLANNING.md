# AR-P003 v0.3 — Sample-Size and Precision Planning Notes

> **Status:** Development planning only — not frozen.  
> **Snapshot:** 2026-09-18  
> The calculations in this note do **not** set the confirmatory reviewer count or case count.

AR-P003 uses a randomized balanced incomplete-block design in which observations are crossed by **reviewer** and **case**. That means ordinary independent-observation sample-size formulas are useful only as a first screening step.

The repository now includes two complementary planning layers:

- `benchmark/arp003_v0_3/plan_sample_size.py`
- `benchmark/arp003_v0_3/planning-scenarios.example.json`
- `benchmark/arp003_v0_3/plan_crossed_design.py`
- `benchmark/arp003_v0_3/crossed-planning-scenarios.example.json`

The first tool remains a fast independent-observation screening approximation. The second uses the repository's balanced incomplete-block assignment structure, simulates reviewer and case random effects, and evaluates the condition contrast with two-way reviewer/case cluster-robust covariance.

See [AR-P003 v0.3 Crossed Reviewer × Case Planning](AR-P003-V0.3-CROSSED-PLANNING.md).

Neither tool freezes a confirmatory sample size.

## Why this tool exists

Before freezing a human study, the project needs to know whether a plausible design is:

- obviously too small to estimate the intended effect;
- likely to require many more reviewer-case observations than expected;
- sensitive to small changes in baseline accuracy;
- more practical if framed around precision rather than a minimum detectable difference;
- limited by reviewer count, case count, or observations per reviewer.

A scenario grid helps expose those tradeoffs before a confirmatory endpoint is chosen.

## Implemented planning modes

### Binary two-group endpoint

For endpoints such as:

- authorization-violation detection accuracy;
- verification-state exact accuracy;
- missing-evidence detection accuracy;

the tool uses a two-sided normal approximation for two independent proportions.

Inputs include:

- control accuracy;
- Receipt-condition accuracy;
- alpha;
- target power;
- design effect;
- attrition/non-usable observation allowance.

The output is an approximate **case-observation count per condition**.

### Standardized continuous endpoint

For a continuous endpoint such as active reconstruction time, the tool can use an assumed standardized mean difference (d).

This is a screening approximation only. Actual timing analysis may require transformation, robust methods, or a crossed-effects model depending on the development data.

### Precision for one proportion

The tool can estimate how many observations would be needed to estimate one proportion to a requested confidence half-width.

### Precision for a condition difference

The tool can estimate an equal-allocation observation count per condition for a requested half-width around a difference in proportions.

## Design-effect adjustment

Because reviewer-case observations are not independent, the tool allows a `design_effect` multiplier.

A design effect greater than 1 increases the required observations.

This is **not** automatically estimated by the current repository. The final design effect must be justified from:

- development-only variance components;
- external evidence that is genuinely relevant;
- or a crossed reviewer/case simulation.

The example file uses `1.5` only as a sensitivity scenario. It is not a frozen estimate.

## Attrition / unusable observations

The planner can also inflate for an expected fraction of unusable observations, such as:

- incomplete submissions;
- timer failures;
- corrupted presentation;
- prespecified technical exclusions.

The example scenarios use 10% only to demonstrate sensitivity.

Difficult, slow, or incorrect responses are not automatically unusable observations.

## Reviewer-equivalent output

When `cases_per_reviewer` is supplied, the tool reports a rough reviewer-equivalent:

```text
ceil(total adjusted case-observations / cases per reviewer)
```

This number is **not** a power calculation for unique reviewers.

It is only a planning translation from case-observations into an approximate reviewer count under the stated workload. The actual crossed design may require more reviewers and/or more cases.

## Illustrative scenario grid

The bundled example scenarios use:

- two-sided alpha = 0.05;
- target power = 0.80;
- design effect = 1.5;
- 10% unusable-observation allowance;
- 8 cases per reviewer.

These are **illustrative assumptions only**.

| Scenario | Adjusted observations / condition | Total case-observations | Rough reviewer-equivalent |
| --- | ---: | ---: | ---: |
| accuracy 0.65 → 0.80 | 230 | 460 | 58 |
| accuracy 0.70 → 0.80 | 489 | 978 | 123 |
| accuracy 0.70 → 0.85 | 201 | 402 | 51 |
| timing, standardized (d = 0.50) | 105 | 210 | 27 |
| difference precision: 0.70 vs 0.80, ±0.07 | 484 | 968 | 121 |

The wide spread is important. A 10-percentage-point accuracy difference can require roughly twice as many observations as a 15-point difference under the same simple assumptions.

That is exactly why the final endpoint/effect target should be frozen **before** data collection.

## Reproducible use

Run the deterministic self-test:

```bash
python benchmark/arp003_v0_3/plan_sample_size.py --self-test
```

Run the bundled scenario grid:

```bash
python benchmark/arp003_v0_3/plan_sample_size.py \
  benchmark/arp003_v0_3/planning-scenarios.example.json
```

A custom config has this form:

```json
{
  "scenarios": [
    {
      "scenario_id": "example",
      "kind": "binary_two_group",
      "p_control": 0.65,
      "p_receipt": 0.80,
      "alpha": 0.05,
      "power": 0.80,
      "design_effect": 1.5,
      "attrition": 0.10,
      "cases_per_reviewer": 8
    }
  ]
}
```

## What still must happen before freeze

The final sample-size/precision requirement remains **open**.

Before it can be marked complete, the project still needs to:

1. use the selected relevant-professional reviewer population as the scope for all planning assumptions;
2. freeze the primary endpoint or small prespecified set of primary endpoints;
3. define a minimally meaningful effect or precision target;
4. obtain development-only estimates for baseline accuracy, timing variability, and reviewer/case clustering in a defensibly related population;
5. decide the reviewer/case allocation, workload, and any experience-band or professional-domain balancing rule;
6. use the crossed-design simulator to evaluate the actual reviewer × case allocation across plausible effect/variance assumptions, then freeze a justified design-specific power/precision analysis;
7. freeze the stopping rule;
8. record the assumptions and resulting reviewer/case counts in the protocol.

The example scenario grid should not be copied into a funding or research claim as though it were the final design.

## Current conclusion

The tool already demonstrates one practical fact: AR-P003 feasibility is highly sensitive to the effect size the study is designed to detect.

A moderate-looking design may be adequate for a large 15-point accuracy change but inadequate for a 10-point change once clustering and unusable observations are allowed for.

The crossed-design simulator now removes one engineering gap: the repository can explicitly model reviewer/case dependence on the actual balanced assignment.

The next useful input is therefore not another generic sample-size formula. It is development-only evidence or a deliberate preregistration decision about:

- likely baseline reviewer performance;
- likely Receipt-condition performance or minimally meaningful improvement;
- reviewer-level variation;
- case-level variation;
- timing distribution;
- realistic cases per reviewer.

Those inputs can then replace the illustrative grid with a defensible frozen design.
