# AR-P003 v0.3 — Leakage and Presentation Audit

> **Status:** Development-only pre-freeze tooling.  
> **Snapshot:** 2026-09-19  
> This audit does not prove that a case is unbiased, realistic, or suitable for confirmatory human testing.

The frozen v0.2.3 benchmark had a known failure mode: incident-class labels were exposed literally in the reviewer evidence, contributing to a ceiling result. v0.3 therefore needs an explicit pre-freeze audit that looks for obvious answer leakage and presentation asymmetry rather than relying only on package structure.

## Tool

```bash
python benchmark/arp003_v0_3/audit_leakage.py <built-runner-dir> \
  --output leakage-audit.json
```

For a pre-freeze fail-closed check on the audit's current **high-risk** rules:

```bash
python benchmark/arp003_v0_3/audit_leakage.py <built-runner-dir> \
  --output leakage-audit.json \
  --fail-on-high-risk
```

The audit runs **analysis-side** because it intentionally joins reviewer-visible presentations with hidden gold labels. The generated report must not be given to reviewers.

## What is checked

### 1. Shared-evidence identity

For each case, the audit hashes the reviewer-visible evidence after deterministic JSON serialization.

If the shared evidence differs between control and Receipt presentations, the audit fails rather than treating the conditions as evidence-symmetric.

This protects the intended contract:

```text
control = shared evidence
receipt = same shared evidence + Receipt
```

### 2. Literal gold incident labels

The audit normalizes punctuation, underscores, case, and whitespace, then searches the shared reviewer evidence for exact gold incident labels.

Example:

```text
gold incident: authorization_violation
visible text:  "authorization violation"
```

This is flagged as:

```text
literal_gold_incident_label_in_control_evidence
```

It is treated as high-risk because literal incident-label exposure was a documented v0.2.3 problem.

### 3. Literal gold actions and sources

Exact normalized action/source labels are also reported when they appear in the shared evidence.

These are **review flags**, not automatic failures, because operation and source identifiers can legitimately be part of raw evidence. Human review must determine whether the case asks for reconstruction from evidence or merely repeats the answer label.

### 4. Degenerate answer options

The runner-bundle builder already records whether every gold set-valued answer is representable.

The leakage audit additionally flags a non-empty answer-option set when:

```text
answer options == gold set
```

for:

- material actions;
- material sources;
- incidents.

That does not prove that a case is invalid, but it removes meaningful discrimination from that structured response field and therefore requires correction or explicit justification before confirmatory freeze.

### 5. Receipt presentation expansion

For each case the audit records:

```text
(shared evidence chars + Receipt chars) / shared evidence chars
```

The current development threshold for a review flag is:

```text
> 1.75
```

This threshold is a **review heuristic**, not a scientific standard and not a frozen exclusion rule.

The purpose is to surface large presentation asymmetry before freeze, not to force conditions to have identical character counts.

## Machine-readable report

Schema:

```text
benchmark/arp003_v0_3/leakage-audit.schema.json
```

The report includes:

- SHA-256 of the build manifest;
- SHA-256 of the hidden analysis bundle;
- per-case stratum;
- observed conditions;
- reviewer-presentation count;
- shared-evidence hash;
- shared-evidence character count;
- Receipt character count;
- presentation expansion ratio;
- answer-option audit metrics;
- literal gold label mentions;
- high-risk flags;
- human-review flags;
- aggregate count of high-risk cases.

## Pre-freeze interpretation

A final sealed corpus should not pass merely because the command exits zero.

Before the `leakage_validation` gate can be marked complete:

1. build the frozen candidate corpus with the final assignment/build tooling;
2. run this audit against that exact build output;
3. preserve the audit report and its hashes;
4. resolve or document every high-risk flag;
5. manually review the reviewer-visible cases for semantic clueing, realism, framing, and task difficulty;
6. ensure any case changes create a new corpus build/hash;
7. rerun the audit after every material case change;
8. freeze the accepted report together with the corpus and analysis plan.

## Known limitations

The audit cannot reliably detect:

- paraphrased answer leakage;
- overly obvious causal wording;
- domain-expert clues;
- implausible or toy-like logs;
- subtle framing effects;
- option-order bias;
- visual salience effects;
- conceptual overlap between evidence wording and the response vocabulary;
- automation bias caused by the Receipt presentation itself.

Those require human methodology review.

## Evidence boundary

Passing this audit means only that the current mechanical checks found no configured high-risk leakage condition.

It does **not** establish:

- a valid human-study instrument;
- absence of all answer leakage;
- ecological validity;
- appropriate statistical power;
- ethics approval;
- a Receipt benefit;
- external or independent validation.
